# RW_3.1a — Calendar Task Drop: Model Layer

## Approval

- [ ] Approved

## Purpose

Erweitert das Datenmodell um `scheduledDate` und `scheduledDuration` auf `LocalTask`, damit Tasks zeitlich eingeplant werden koennen OHNE einen FocusBlock (EventKit-Event) zu erstellen. Dies ist die Grundlage fuer alle weiteren Phasen von RW_3.1.

## Implementation Details

### 1. LocalTask.swift — Neue Properties

```swift
// MARK: - Direct Scheduling (RW 3.1)

/// Date when this task is scheduled on the timeline (nil = not scheduled).
/// MUTUALLY EXCLUSIVE with assignedFocusBlockID — a task cannot be both
/// scheduled independently AND assigned to a FocusBlock.
var scheduledDate: Date?

/// Duration override for scheduled display in minutes (nil = use estimatedDuration or default 30).
var scheduledDuration: Int?
```

**Platzierung:** Nach Zeile 129 (nach `progressNote`), vor MARK AI Task Scoring.

**Computed Property:**
```swift
/// Whether this task is directly scheduled on the timeline (not via FocusBlock).
var isScheduled: Bool { scheduledDate != nil }
```

**Init:** Beide Felder werden NICHT zum init hinzugefuegt — sie sind Optional mit SwiftData Default `nil`. Bestehende Call-Sites bleiben unveraendert.

**CloudKit:** Optional-Felder mit nil-Default sind automatisch CloudKit-kompatibel. Keine Migration noetig — SwiftData Lightweight Migration handled neue Optional-Properties.

### 2. PlanItem.swift — Mirror Properties

```swift
// Direct Scheduling (RW 3.1)

/// Scheduled date on timeline (nil = not scheduled)
let scheduledDate: Date?

/// Scheduled duration override in minutes
let scheduledDuration: Int?

/// Whether this task is scheduled on the timeline
var isScheduled: Bool { scheduledDate != nil }
```

**init(localTask:)** — Zeile nach `self.blockerTaskID`:
```swift
self.scheduledDate = localTask.scheduledDate
self.scheduledDuration = localTask.scheduledDuration
```

**init(reminder:)** — Zeile nach `self.blockerTaskID`:
```swift
self.scheduledDate = nil
self.scheduledDuration = nil
```

### 3. TimelineItem.swift — Neuer ItemType Case

```swift
enum ItemType: Sendable {
    case event(CalendarEvent)
    case focusBlock(FocusBlock)
    case scheduledTask(id: String, title: String)  // Lightweight — kein LocalTask-Ref (nicht Sendable)
}
```

**Neuer Initializer:**
```swift
/// Creates a TimelineItem from a scheduled LocalTask.
/// Uses scheduledDate as start and scheduledDate + duration as end.
init(scheduledTaskID: String, title: String, scheduledDate: Date, durationMinutes: Int) {
    self.id = "scheduled_\(scheduledTaskID)"
    self.startDate = scheduledDate
    self.endDate = Calendar.current.date(
        byAdding: .minute, value: durationMinutes, to: scheduledDate
    ) ?? scheduledDate
    self.type = .scheduledTask(id: scheduledTaskID, title: title)
}
```

**ID-Prefix `scheduled_`:** Verhindert Kollisionen mit CalendarEvent/FocusBlock IDs die denselben String nutzen koennten.

**Keine Aenderungen an `groupOverlapping()` oder `assignColumns()` noetig** — beide arbeiten auf `startDate`/`endDate` generisch. Der neue Case wird automatisch in Collision Detection einbezogen.

## Expected Behavior

- **Input:** LocalTask mit gesetztem `scheduledDate` und optional `scheduledDuration`
- **Output:** PlanItem mit `isScheduled == true`, TimelineItem mit `.scheduledTask` type
- **Side effects:**
  - SwiftData Schema-Migration (automatic lightweight — neue Optional-Felder)
  - CloudKit sync fuer neue Felder (automatisch)

## Business Rules

1. **Mutual Exclusion:** `scheduledDate != nil` und `assignedFocusBlockID != nil` duerfen NICHT gleichzeitig gesetzt sein. Enforcement passiert in Phase B (Write-Sites), nicht im Model.
2. **Default Duration:** Wenn `scheduledDuration == nil`, wird `estimatedDuration ?? 30` verwendet (Logik in Phase B/C, nicht im Model).
3. **Bestehende Tasks:** Alle existierenden Tasks bekommen `scheduledDate = nil`, `scheduledDuration = nil` — kein Breaking Change.

## Known Limitations

- Mutual Exclusion wird NICHT im Model enforced (CloudKit kann keine Constraints)
- `scheduledDuration` hat keinen Validator (negative Werte theoretisch moeglich) — wird in Phase B an Write-Sites validiert
- TaskSourceData Protokoll wird NICHT erweitert — scheduledDate ist kein Protokoll-Concern
